# 03. Статический анализ DOS-версии — основной маршрут

## Принцип

Не начинать с Ghidra «проанализируй игру целиком». Сначала составить байтовый каталог и гипотезы о структуре. Статическая декомпиляция — основной путь выяснить **какие** таблицы, формулы и ветки есть в движке; эксперименты подтвердят **что они значат**.

## Шаг S0: инвентаризация и воспроизводимость

1. Получить законную копию файла/диска и сохранить оригинал без правки в `private/game-dos/`.
2. `python scripts/inventory.py private/game-dos --out artifacts/inventory.json`.
3. В отчёте отметить размер каждого файла, SHA-256, первые байты, кандидатов на MZ (`MZ`/`ZM`), `.COM`, количество печатных строк, entropy блоков (если добавлены отдельным анализатором), архивы, размер и время изменения.
4. Не доверять расширению `.EXE`: проверить magic. `.COM` не имеет MZ-заголовка и может быть просто сырым x86 кодом/данными.
5. В отдельной копии попробовать запустить игру в DOSBox. Вести журнал открытых/созданных файлов (в DOSBox-X доступно логирование INT 21h/дискового ввода — зависит от сборки).

**Выход:** `artifacts/inventory.json`, `knowledge/FILES.md`, отметка о версии дистрибутива. Пока нет входного файла, все результаты S0 — `unknown`.

## Шаг S1: классификация исполняемого файла

Для DOS MZ:
- `e_cblp`, `e_cp` — размер объявленной EXE-части;
- `e_cparhdr` — заголовок в параграфах (16 байт);
- `e_crlc`, `e_lfarlc` — таблица перемещений;
- `e_cs:e_ip`, `e_ss:e_sp` — начальные регистры;
- размер и возможный хвост после объявленного EOF (возможен overlay/данные/пакер, но сам по себе хвост не доказательство).

Важно: адреса real mode на диске и после DOS loader отличаются. Сначала определять load segment, затем учитывать DOS MZ relocations. Смещения Ghidra — пространство её программы, которое **не тождественно** `CS:IP` при живом запуске.

Вопросы: есть ли Borland/Watcom/Microsoft runtime signature, overlays, самораспаковка, overlay manager, cross-segment far calls, DOS extender. `strings` не является полным доказательством текстов: данные могут быть кодировкой CP437, текстом с собственным набором шрифтов, 16-битными указателями или сжатыми.

## Шаг S2: импорт Ghidra

1. В GUI **проверить выбранный loader/language**: 16-bit x86 real mode, если соответствует фактическому бинарнику. Убедиться, что entry point и сегменты разумны; при ошибочном импортировании автодекомпиляция не спасёт.
2. Сохранить исходные предположения и скрин Property / Memory Map / Entry point.
3. Сделать headless-анализ одного файла без переписывания исходника:

```powershell
$GHIDRA_HOME = 'C:\Tools\ghidra'
$PROJECTS = 'C:\OE\ghidra-projects'
$BINARY = 'C:\OE\private\game-dos\GAME.EXE'  # заменить ПОСЛЕ S0 на реальное имя
& "$GHIDRA_HOME\support\analyzeHeadless.bat" $PROJECTS OperationEurope -import $BINARY -analysisTimeoutPerFile 1200 -log 'C:\OE\artifacts\ghidra.log'
```

Здесь путь/имя — **шаблон, не найденный файл**; директории должны существовать. Сначала GUI-check, потом batch.

4. Экспортировать карту памяти, список функций, число references, пересечения строк xrefs, подозрительные массивы `dw`, `db`, `dd` и список `far call`/jump tables. Экспорт — скриптом Ghidra или вручную, один раз отладить скрипт на небольшом бинарнике.
5. Найти части программы: инициализация, ввод, вывод, файловые сохранения, UI, сценарии, механика хода, бой, PRNG, AI. Не переименовывать функции, не сохранив evidence.

Прямые ссылки на Headless API — `docs/02_SOURCES.md`. Несовместимость конкретной версии Ghidra с пакером решать отдельно, а не объявлять, что игра недекомпилируема.

## Шаг S3: искать таблицы по сигнатурам, но не угадывать

Генерировать кандидаты по следующим наблюдениям:

- Серии однотипных записей постоянного шага `8, 12, 16, 20, ...` байт.
- Строковые массивы имён генералов/техники и соседние numeric fields.
- Ряды небольших целых чисел, похожих на боевые характеристики, но **отличать от графических данных**.
- Cross-references: код индексирует таблицу через `base + index*stride`, затем читает поля фиксированных смещений.
- Для little-endian использовать оба варианта `uint8`/`uint16` (и `int16` для отрицательных поправок); не принять экранное число за исходное без проверки масштаба.

### Типовая запись гипотезы

```text
ID: TABLE-001
Source file sha256: [sha256]
File offset: 0x????
Ghidra address: ??:???? (mapping recorded separately)
Record width: candidate 12 bytes
Count: candidate 45
Field +00: candidate equipment_id/u16
Field +02: candidate attack/u8
References: FUN_??? + [evidence]
Confidence: inferred
Disproof: adjacent records violate expected ranges
```

Не публиковать raw таблицы из оригинальной игры без отдельного правового решения; репозиторий может хранить **метаданные, схемы и описание**, при необходимости производить экспорт при наличии локальной игры.

## Шаг S4: идти от видимого числа к функции

1. Выбрать конкретный хорошо читаемый параметр (например strength или fuel). Зафиксировать видимое число и сцену.
2. Найти RAM candidates (см. `04_DYNAMIC_LAB.md`), отличить дубликат в UI-buffer от игрового объекта.
3. Записать runtime `DS:offset` и mapping соответствующих data сегментов.
4. Через Ghidra и DOSBox-X определить, где поле **читается** и **записывается**.
5. Локализовать цикл обновления. Установить условия, время жизни структуры, связь со сценарием и с сохранением.
6. Для найденной функции выделить входы/выходы и side effects. Создать таблицу test cases.

## Шаг S5: PRNG и арифметика

Искать стандартные шаблоны `rand`, линейный конгруэнтный генератор, битовые сдвиги, вызовы BIOS/RTC/таймеров, но не навязывать конкретную реализацию. После идентификации локализовать состояние генератора, длину последовательности, источник начального seed, места обращения. Контролируемые тесты с seed воспроизводить и сравнивать с гипотезами о формулах. В 16-битном коде важно сохранять целочисленные переполнения, знаковость, порядок операций и округление при переносе в JS.

## Шаг S6: выгрузка и проверка

Для каждого результата обязательно:
- конкретная версия файла/SHA-256;
- file offset или явно `runtime only`;
- адрес Ghidra и mapping;
- что наблюдалось и какой код обращается;
- тест, подтверждающий интерпретацию поля;
- степень уверенности и возможные альтернативы.

### Типичные ошибки

- Заменить `uint16` на JS number без `& 0xffff` и получить другие переполнения.
- Принять `DS:1234` за абсолютное `0x1234`.
- Принять bitmap/tilemap за плотную таблицу оружия.
- Упустить overlay, который подгружается только на конкретном экране.
- Списать всю неизвестную ветку на RNG.
- Включить в базу имена/числа из Genesis dump и назвать это подтверждёнными DOS-данными.
