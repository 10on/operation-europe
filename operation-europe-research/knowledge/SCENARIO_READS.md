# Проверенные чтения при выборе сценария

Источник: DOS main.exe SHA-256 `0b33be2fd37b965e5b92d1881f34226c1608eff6d0358787a7cb5049f218e9df`. DOSBox-X, API отладчика; оригинал не изменён. Все file offsets ниже десятичные, от начала файла.

Ввод: `space enter`, затем N раз `down`, затем `enter enter`. Названия сценариев не снимались; строки таблицы обозначают последовательности ввода, не исторические кампании.

| N | SCEDATA offset | Прочитано | Байт буфера +1 | MAPINF.DAT offset | Прочитано | Доказательство |
|---|---:|---:|---:|---:|---:|---|
| 0 | 17743 | 8143 | 0 | 0 | 1600 | TASK-010/run-20261030T010340Z |
| 1 | 25886 | 8143 | 1 | 1600 | 1600 | TASK-014/run-20261030T043316Z |
| 2 | 34029 | 8143 | 2 | 3200 | 1600 | TASK-015/run-20261030T050321Z |

В каждом случае открывались SCEDATA и MAPINF.DAT, возвращался handle 9, AX после read равнялся размеру, а полные буферы совпали с соответствующими срезами файлов. Проверка: `scripts/verify_runtime_reads.py RUN SCEDATA_OFFSET MAPINF_OFFSET`. Отчёты содержат SHA и пути артефактов.

Статический код: SCEDATA seek `9600 + (entry_AX & 255)*8143`; MAPINF seek `(byte DS:0043 & 127)*1600`. Таблица подтверждает три конкретных исполнения, не все допустимые значения. Геометрия карты, число сценариев и смысл полей из размера блоков не следуют.

Отдельно TASK-011 проверил чтение первого 800-байтового участка SCEDATA функцией file 0xD1C6 при AL=1. Это другой reader, его не смешивать с таблицей выше.
