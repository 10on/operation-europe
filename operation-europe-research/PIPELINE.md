# Operation Europe — master pipeline для Windows + Mac + облачного ревью

Версия: 0.1 (2026-10-25). Исследование не запускалось: файлы оригинальной DOS-игры отсутствуют. В этом документе **план**, а не отчёт о найденных таблицах. Прежде чем действовать, оба локальных агента читают `AGENTS.md` и соответствующие файлы `agents/`.

## Что мы в итоге хотим получить

Не сборник скриншотов и не эмулятор в браузере с неудобным управлением, а восстановленную независимую логику Operation Europe: карта, подразделения, вооружение, приказ, переход хода, снабжение, атака и компьютерный противник. Затем новый UI, адаптированный для мыши и клавиатуры, со своими материалами и локализацией. Работа проводится в первую очередь на DOS-версии, а знакомую Genesis-версию сверяем выборочно, не предполагая идентичные реализации.

## Канонический порядок

```text
00. Приём и fingerprint оригинальных DOS-файлов
  -> 01. Определение MZ/COM/данных/overlays/пакера
    -> 02. Пробный импорт в Ghidra (loader, сегменты, entry)
      -> 03. Инвентаризация xrefs/таблиц/строк/функций
        -> 04. Выбор одного видимого игрового параметра
          -> 05. DOSBox Automation: frame, действия, RAM-candidates
            -> 06. DOSBox-X: точка остановки/читатели/писатели
              -> 07. Структура данных + функция + два независимых теста
                -> 08. Схема/парсер/тест порта
                  -> 09. Следующая система механики
```

Ветвление на Mac происходит на шагах 04–05: если frame требует понимания GUI, Windows передаёт кадр/crop Mac для OCR/Qwen. Это **не** переводит работу целиком в Vision. Не тратить дорогую модель на генерацию 30 вариантов одного пиксельного числа.

## Какие вопросы решаются каким инструментом

| Вопрос | Первичный способ | Подтверждение | Исполнитель |
|---|---|---|---|
| «Из чего состоит дистрибутив?» | inventory.py | sha256 + ручная проверка | Windows |
| «Где entry point?» | MZ header + Ghidra | отладчик | Windows |
| «Какие есть таблицы?» | xrefs + паттерны доступа | RAM + GUI | Windows |
| «Что за экран?» | ROI/templates/Tesseract | Qwen3-VL | Mac |
| «Какое число показано?» | OCR/tile-glyph + crop | память/ручная разметка | Mac + Windows |
| «Как работает MOVE?» | xrefs + step | повтор игры | Windows |
| «Как работает бой?» | дизассемблирование/PRNG | управляемые серии игр | Windows |
| «Какую гипотезу проверить?» | компактные отчёты | cloud reviewer | Облако |
| «Порт точен?» | golden fixtures | differential tests | Windows/CI |

## Фаза 1. Фиксируем исходники исследования

Создать `private/game-dos` (нет в репозитории). Запустить `inventory.py`. Установить конкретную DOS-версию: регион/язык, хеш, способ запуска. Если EXE упакован, отличать упаковку от стандартного MZ/оверлеев по **признакам**; никогда не скачивать «универсальный unpacker» с сомнительного сайта. В первой базе знаний создать `FILES.md`, `BINARY_MAP.md` и `ENVIRONMENT.md`. Они должны быть редактируемыми файлами с датой, версиями и степенью уверенности.

Критерий прохождения: один и тот же мастер-дистрибутив хешируется одинаково на Windows и на резервной копии; ни один исходник не изменился в результате запусков.

## Фаза 2. Получаем карту кода, а не фантазии о структуре

Импортировать EXE через Ghidra GUI, проверить соответствие MZ и сегментов, получить список функций/ссылок на строки и данные. Не отправлять LLM мегабайты декомпиляции: искать кандидатов прицельно, формировать компактный `function_id + file offset + pseudo-code excerpt + xrefs`. При подозрении на позднюю подгрузку overlay провести эксперименты с целевым экраном. Исправлять неверные разметки функций только с описанием основания, чтобы другой агент мог проверить разницу.

Критерий: текущая гипотеза о таблице имеет **record stride + count candidate + не менее одного code xref + disproof test**; иначе таблица остаётся подозрительным массивом.

## Фаза 3. Пересечение GUI и памяти

Получить screenshot выбранной карточки подразделения. Mac возвращает JSON с видимыми числами и координатами ROI, а Windows пробует искать эти числа в RAM в width 1/2/4 и с допустимыми масштабами. Найти различие между UI buffer и игровыми объектами: закрыть окно, выбрать другое подразделение, изменить параметр и сравнить кандидатов. Если адреса исчезают после перезапуска, искать pointer chain/относительные смещения, а не хранить голый абсолютный адрес в коде порта.

Критерий: кандидат прошёл минимум две конфигурации и один проверяемый тест на изменение **именно искомого поля**.

## Фаза 4. Восстановление конкретных механик

Начать с движения: короткое, видимое, мало RNG. Определить порядок «валидация приказа -> вычисление доступной дистанции -> списание ресурсов -> перемещение -> записи в журнал -> AI/переход хода». Записывать реальный код для каждого подозреваемого шага, затем вызывать/проверять в изоляции. Лишь после этого переходить к снабжению, бою и AI. Для вероятностных формул искать PRNG и его вызовы, а не подбирать коэффициент по двум потерям.

Критерий: указана версия EXE, сигнатура функции, обработка 8/16-битных знаков и переполнений, есть воспроизводимая вход/выход пара.

## Фаза 5. Прототип independent engine

Сначала TypeScript пакет `engine` с функцией `step(state, action) -> state/events` и JSON fixtures. Пока UI нет, прогонять тесты CLI с ожидаемым изменением координат/ресурса. Держать game-engine state и визуальный renderer отдельно. Сохранения — версионированные, предусмотрена миграция. Отдельно записывать случаи, где данные/правила DOS и Genesis расходятся.

## Стандарт выхода одного локального task

```text
Task ID / Owner / Program version / Binary SHA
Goal / bounded steps performed / visible result
Claims (confirmed / observed / inferred / unknown)
Evidence (sha256 + relative paths + addresses as appropriate)
Competing explanations / next discriminating test
Report schema validation / status
```

Любой материал с бинарными смещениями указывает, **к чему это смещение относится**: исходный файл, загруженный image offset, физический RAM адрес, реальный `CS:IP`, Ghidra address. Неверная координатная система обнуляет ценность открытия.

## Бюджет времени и токенов

- По умолчанию первая попытка — локальный анализатор и скрипт, не LLM.
- Простой разбор скриншота 320×200 — сначала templates + OCR, Qwen-VL только при semantic ambiguity.
- Облачный агент получает summary и **один вопрос** для принятия решения. Глубокий disassembly переносить только для спорных функций, не для рутинных.
- Не писать long-running «автономную игру» без шаговых assert и ограничений. Самостоятельный бот обязан останавливаться на неожиданном экране.
- Логи и дампы не обрезать до утраты проверяемости локально; в облако отправлять только выбранные фрагменты.
